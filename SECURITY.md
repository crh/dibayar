- 2026-07-17: Recipient invoice share-link (Task F, local implementation, uncommitted, NOT applied/deployed) — historical, see the 2026-07-18 entry above for current status. Threat model: the share link is a bearer-token capability — anyone holding the URL can view the invoice's safe-field JSON/PDF via `/i/[token]` with no login. Controls: the token is 32 bytes of random data (256 bits of entropy) encoded base64url, generated with a CSPRNG; only its SHA-256 hash is stored, so a database read alone cannot reconstruct a usable link; the public routes return a safe field projection (no owner PII beyond what a recipient needs, no internal IDs beyond the invoice itself); regenerating a share invalidates the prior token (old hash no longer matches); revoke deletes the share row outright; every public response sets `no-store`, `noindex`, and `no-referrer`/no-referrer-leak headers; and there are best-effort per-instance rate limits on the public routes to blunt brute-force token guessing. Caveats, stated honestly: the rate limiter is in-process/per-instance only, not distributed, so it does not bound abuse across multiple server instances; the feature has not been verified against any real database or deployed runtime — migration `20260717090000_invoice_share` exists but was not applied anywhere, and no external (non-localhost) smoke has occurred. Public recipient usability cannot be verified while the only reachable environment (protected Preview) remains behind Vercel SSO; that verification, and any decision to expose the route beyond SSO, are both explicitly pending and separately approval-gated. Production is untouched.
- 2026-07-17: Task D code-hardening review (DAILY_LOG "Day 1 Task D — code hardening and clean-checkout verification — 2026-07-17"), in two parts. Part 1, commit `1154c51`: `GET /api/deals`, `GET /api/deals/[id]`, and `DELETE /api/deals/[id]` had no try/catch, so an unhandled DB error would escape as an uncaught exception instead of the generic Bahasa 500 JSON body (`{error: "..."}`, no stack/detail) that `GET /api/invoices`, `GET /api/invoices/[id]`, and `GET /api/invoices/[id]/pdf` already return and test for. All three deal routes now match that controlled-error pattern. Part 2, a reviewer-found correction to this same Task D, commit `3129b6a`: the claim that malformed-input handling was "already sound" was wrong on two counts, both now fixed in the deal and invoice POST/PATCH mutation handlers (`src/app/api/deals/route.ts`, `src/app/api/deals/[id]/route.ts`, `src/app/api/invoices/route.ts`, `src/app/api/invoices/[id]/route.ts`). First, every mutation handler called `request.json()` inside a catch block that only special-cased `ZodError` as 400, so syntactically malformed JSON threw an uncaught `SyntaxError` that fell through to the generic 500 branch instead of a 400; each handler now also catches `SyntaxError` and returns the route's existing 400 validation-error message (no parser detail, no `fields` key, since there is no Zod error to flatten). Second, each handler called `auth()` (and, on the deal `PATCH`/`DELETE` routes, `context.params`) outside its try/catch, so an auth-infrastructure rejection (e.g. `auth()` throwing) would escape as an uncaught exception instead of the route's own generic Bahasa 500 JSON; `auth()` and `params` are now called inside the same try block so infrastructure failures map to the existing operation-specific 500 message, with the explicit 401-on-no-session check unchanged and still returned before any mutation is attempted. Tenant scoping (every query still filters by session `userId`), transaction atomicity, and the deal-deletion FK-restrict path were reviewed again and no further defect was found.
