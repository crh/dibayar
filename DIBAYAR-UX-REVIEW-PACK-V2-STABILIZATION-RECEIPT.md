## 11. J35 disposition (Workstream D)

**Faithfully captured as a genuine success**, not retained as an environment limitation. The original "clipboard fails in headless Chromium" conclusion was investigated and found to be wrong: `navigator.clipboard.writeText()` works correctly in this environment. The actual bug was in the test's own detection — `ShareLinkField`'s copy button carries a fixed `aria-label` ("Salin tautan invoice") that never changes, while only its *visible text* flips `Salin → Tersalin` on success. The original assertion, `page.getByRole("button", { name: "Tersalin" })`, matches by *accessible name* (which `aria-label` overrides), so it could never match this button regardless of outcome — every successful copy was silently misreported as a failure. (A second, now-irrelevant red herring was also found and is documented in the test's own comments: `page.getByRole("alert")` used in the original error-detection also happened to match Next.js's own always-present, invisible route announcer.) Fixed by matching on the button's actual accessible name (`"Salin tautan invoice"`, stable across states) and reading its visible text to determine outcome. `J35-invoice-share-link/03-copied-mobile375.png` now shows the real "Tersalin" success state, verified across 4+ repeated runs.

## 12. `/deal/[id]` status-code conclusion (Workstream E)

**Expected Next.js App Router streaming behavior — confirmed root cause, not a routing bug or test-observation artifact.** `src/app/(app)/loading.tsx` was written specifically as the home page's ("Beranda") own loading skeleton, but because it lives at the `(app)` route-group level, Next.js applies it as an implicit Suspense boundary to *every* route under that group, including `/deal/[id]` (and, by the identical mechanism, `/invoice/[id]`). Per Next.js's own documented `notFound()` behavior ("Because the check runs inside the Suspense boundary, the response has already begun streaming as a 200, and the status can't change once streaming has started"), the response commits to HTTP 200 before the nested page's `notFound()` call is reached — even though `deal/[id]/page.tsx` calls it synchronously and early, before returning any JSX. Verified experimentally: temporarily removing `(app)/loading.tsx` and rebuilding made the same not-found request return a genuine 404; the file was then restored and the app rebuilt again, so no product behavior changed as a result of this investigation.

**Recommended fix (not implemented this session, per the task's scope boundary):** give `deal/[id]` and `invoice/[id]` their own route-specific `loading.tsx` files (removing them from `(app)/loading.tsx`'s implicit scope), or move the existence check earlier (middleware/proxy). Either is more than a one-line change and touches shared routing/loading-state behavior, so it was left for a dedicated engineering session rather than folded into this evidence-capture pass.
